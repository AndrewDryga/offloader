Self-hosted REST endpoints for warehouse data

Stop sending the same product API reads to your warehouse.

Your warehouse builds the data. Your product should not query it on every request. Offloader serves snapshots from REST endpoints on your own servers — so repeat reads stay cheap until the next refresh.

How it works

Build the data once.
Read it many times.

Your pipeline exports the answer set to S3 or GCS. Offloader loads it and handles API reads until the next snapshot is ready. The warehouse is used by the export job, not by each customer request.

  1. 01

    You publish a snapshot

    Export the data to Parquet in S3 or GCS with a small manifest. Pick the freshness you need: 15 minutes, hourly, daily.

  2. 02

    Offloader checks and loads it

    The container checks the files and schema, then loads the configured snapshot into DuckDB before serving requests.

  3. 03

    Your app calls a REST endpoint

    API keys choose the endpoints and tenant. Each endpoint defines the columns it can return. Callers send filters, never SQL.

  4. 04

    A newer snapshot swaps in

    When a newer snapshot passes validation, Offloader switches to it without taking the API down. If it fails, the last good snapshot keeps serving.

Your options

Three ways to serve
warehouse data to your app.

Choose by how fresh the data must be and how often the same requests repeat. If snapshots fit, Offloader does the work around the query: loading exports, checking schemas, enforcing tenant access, and staying up during refreshes.

  • Query the warehouse

    Keep this path for ad-hoc queries or data that cannot wait for the next snapshot.

  • Add a response cache

    A smaller change when the same requests repeat. Cache misses still use your existing API.

  • Serve snapshots with Offloader

    Every request reads a published snapshot. You run the container and schedule the exports.

FAQ

The questions we actually get.

How it’s different

Isn’t this just a cache in front of my warehouse?

Not quite. A response cache reuses earlier answers. A miss still reaches the warehouse if that is what your API calls today. Offloader answers from a snapshot, including on cache misses. Its endpoint definitions and API keys control which columns and tenant rows a caller can read.

We already run a CDN in front of it — isn’t that enough?

Keep the CDN. It helps when many users ask for the exact same response. The problem is the origin behind the CDN. If a cache miss still goes to the warehouse, a busy endpoint can still send millions of reads to metered compute. Offloader makes the origin a small service you run. It emits proper ETag/Cache-Control headers, so the CDN keeps caching, and the misses land on Offloader instead of the warehouse.

How is this different from Databricks Lakebase?

Lakebase is managed Postgres inside Databricks. It can be the right answer if you are all-in on Databricks, need read-write tables, or want Postgres clients. Offloader is narrower: one self-hosted, read-only container that serves approved Parquet snapshots from Snowflake, BigQuery, Redshift, Spark, Databricks, or any pipeline that can write the files. The API is REST, not Postgres. The trade is narrower scope, simpler deployment, and no managed database bill for this read path.

Couldn’t we build this ourselves?

Yes, if the scope is small. DuckDB behind an HTTP handler is not the hard part. The expensive part is everything that makes it safe to run: rejecting half-written exports, checking schema changes, swapping snapshots without downtime, preventing tenant bypass, keeping the last good snapshot on failure, generating docs, and exposing diagnostics. Offloader handles those parts for you.

How is this different from ClickHouse, Tinybird, or warehouse-native acceleration?

Use a dedicated serving database when you need live OLAP, ad-hoc queries, or a new serving data model. Offloader is for the narrower case: the warehouse already produced the answer set, the API shape is known, and the data can wait for the next snapshot. Your warehouse remains the source of truth; Offloader serves its snapshots on servers you run.

Will it fit your data

How fresh is the data?

Freshness depends on your export and refresh schedule. Each successful data response includes its snapshot ID, the time its data was current (the watermark), and a stale flag. Your app decides whether the data is fresh enough. Offloader keeps serving an old snapshot if a refresh fails; it does not enforce a maximum age. If you need data within seconds, use a streaming or transactional system.

How do isolation and security work?

The API key decides what a caller can read. The server inserts the tenant filter before the query runs, so the caller cannot widen it. Keys are stored as SHA-256 hashes, endpoints are allow-listed per key, and a public (auth: none) mode is only accepted when no endpoint is tenant-scoped. Offloader runs in your environment, where you control API access. The optional managed CDN is for public data only. Read the security model →

My data is per-user — can a snapshot handle the cardinality?

Usually, yes. Many customers can share a snapshot; their API keys limit which rows each can read. Size the servers for your data, queries, and peak traffic, then test with realistic customer requests. On a 4-vCPU reference server, 67 datasets (5.8 GB) used about 600 MB of RAM when idle and up to 2.1 GB when every request missed the cache (sizing guide). If the working set will not fit a reasonable server, partition the snapshots or choose another approach.

Which warehouses does it work with?

Any source that can publish Parquet plus a small manifest: Snowflake, BigQuery, Redshift, Spark, Databricks, or your own pipeline. Offloader does not query the warehouse when a user calls your API. It reads only the snapshots you publish.

What does it actually take to run?

You run the container and provide the snapshot files. The real cutover shown under Pricing runs on two small instances and serves about 136 million requests a month, with 94% answered by the CDN. Your instance size depends on the data, query cost, traffic peaks, and cache hit rate. Start with the benchmark, then test your own workload.
